# 前端展示对接文档

## 1. 文档目标

本文档面向 C 前端负责人，用于明确 AutoTestDesign 的前端页面需要接收什么输入、展示什么内容、允许设计者修改什么内容，以及每个页面对应的后端接口。

前端的核心目标不是展示静态结果，而是让设计者完成以下交互式测试设计链路：

```text
需求输入
-> 结构化解析
-> 风险评分
-> 覆盖目标识别
-> 覆盖策略选择
-> 测试用例生成
-> Oracle 复核与 FSM 路径审查
-> 人工审查与修订
-> 差量再生成
-> 结果分析
-> 测试套件优化
-> 导出
```

AutoTestDesign 是**通用型测试设计工具**。前端展示对象应围绕设计者输入的被测系统需求展开，不应把某一个固定 AUT 写死到页面文案、接口字段或展示逻辑中。

## 2. 页面与接口总览

| 页面或模块 | 设计者输入 | 前端展示 | 后端接口 | 关键请求/返回字段 |
|---|---|---|---|---|
| 输入与结构化解析页 | 文本粘贴或文件上传 | 上传状态、输入预览、需求条目、字段完整度、结构化需求表 | `POST /ingest`、`POST /ingest/file`、`POST /parse` | `/ingest` 请求 `content: string`；`/ingest/file` 请求 `file: file`；`/parse` 请求 `requirement_text: string`，PDF/DOCX 上传后可传空字符串，返回 `requirements`、`analyzed_requirements`、`prompts_used` |
| 风险评分页 | 已解析需求 | 风险项数量、高风险数量、P1 数量、风险热力图、风险评分表 | `POST /risk` | 请求 `analyzed_requirements: array<AnalyzedRequirement>`；返回 `risk_analysis`、`prompts_used` |
| 覆盖项与覆盖策略页 | 已解析需求、风险评分结果 | 覆盖目标数量、覆盖项表、EP/BVA/DT 数量、策略理由与技术理由 | `POST /coverage`、`POST /strategy` | `/coverage` 返回 `coverage_goals`；`/strategy` 返回 `coverage_items` |
| 测试用例与状态路径页 | 覆盖项、风险评分结果、需求数据 | 测试用例池、状态筛选、技术筛选、追溯筛选、FSM 图、Oracle 复核表 | `POST /generate`、`POST /fsm`、`POST /oracle` | `/generate` 返回 `test_design_specs`、`test_cases`；`/fsm` 返回 `fsm`；`/oracle` 返回 `oracle_results` |
| 生成依据与差量改进页 | 修订记录、当前设计结果 | Prompt 证据、本地修订记录、差量更新结果、追溯分析 | `POST /regenerate`、`POST /analysis` | `/regenerate` 返回 `created`、`updated`、`unchanged`、`deprecated`；`/analysis` 返回 `analysis_results`、`summary` |
| 测试套件优化与导出页 | 已生成测试用例、风险评分、覆盖项、导出格式 | 优化前后数量、删除候选、导出预览、下载状态 | `POST /optimize`、`POST /export` | `/optimize` 返回 `optimization_result`；`/export` 按 `format` 返回文件流 |

## 3. 前端必须支持的输入

| 输入类型 | 前端要求 | 校验要求 | 交给后端的字段与类型 |
|---|---|---|---|
| 文本粘贴 | 多行文本框，显示文本预览 | 非空、长度提示 | `POST /ingest`，JSON 字段 `content: string`；随后 `POST /parse`，JSON 字段 `requirement_text: string` |
| TXT/MD 文件 | 文件上传，显示文件名和文件大小 | 文件类型、空文件、编码错误 | `POST /ingest/file`，multipart 字段 `file: file`；前端读取文本内容后调用 `POST /parse` |
| PDF 文件 | 文件上传，显示文件名和文件大小 | 文件类型、空文件、解析依赖可用性 | `POST /ingest/file`，multipart 字段 `file: file`；随后 `POST /parse`，JSON 字段 `requirement_text: ""` |
| DOCX 文件 | 文件上传，显示文件名和文件大小 | 文件类型、空文件、解析依赖可用性 | `POST /ingest/file`，multipart 字段 `file: file`；随后 `POST /parse`，JSON 字段 `requirement_text: ""` |

前端不负责解析 PDF/DOCX 二进制文件语义。文本粘贴和 TXT/MD 文件由前端把实际文本传入 `/parse`；PDF/DOCX 文件先通过 `/ingest/file` 上传原始文件，再调用 `/parse` 并传入空字符串，由后端在解析阶段读取 ingest 暂存内容。

## 4. 前端必须展示的数据对象

| 数据对象 | 必须展示字段与类型 | 是否可编辑 | 当前编辑方式 |
|---|---|---|---|
| DisplayRequirement | `requirement_id: string`、`module: string`、`raw_requirement: string`、`description: string`、`source: string`、`input_fields: array<string>`、`data_ranges: array<string>`、`conditions: array<string>`、`business_rules: array<string>`、`expected_action: string`、`confidence: number`、`missing_fields: array<string>` | 可编辑 | 前端本地记录 RevisionLog |
| RiskEntry | `requirement_id: string`、`impact: number`、`likelihood: number`、`score: number`、`level: enum<High, Medium, Low>`、`test_priority: enum<P1, P2, P3>`、`reason: string` | 可编辑 | 前端本地记录 RevisionLog |
| CoverageGoal | `coverage_goal_id: string`、`requirement_id: string`、`goal: string`、`related_inputs: array<string>`、`related_conditions: array<string>`、`expected_action: string` | 只读 | 作为 `/strategy` 输入 |
| CoverageItem | `coverage_item_id: string`、`coverage_goal_id: string`、`requirement_id: string`、`description: string`、`technique: enum<EP, BVA, DT>`、`conditions: array<string>`、`data_ranges: array<string>`、`input_fields: array<string>`、`expected_action: string`、`strategy_rationale: string`、`technique_reason: string`、`status: enum<ai_generated, human_revised, human_added, rejected>` | 可新增、修改、拒绝 | 前端本地记录 RevisionLog |
| TestCase | `test_id: string`、`requirement_id: string`、`coverage_item_id: string`、`spec_id: string`、`technique: enum<EP, BVA, DT>`、`title: string`、`preconditions: array<string>`、`input_data: object`、`test_steps: array<string>`、`expected_result: string`、`standard_ref: string`、`priority: enum<P1, P2, P3>`、`status: enum<Draft, Approved, Rejected>` | 可编辑 | 前端本地记录 RevisionLog |
| FsmResult | `states: array<string>`、`transitions: array<object>`、`coverage_paths: array<string>`、`mermaid: string` | 路径覆盖状态可审查 | 前端本地记录 RevisionLog |
| OracleResult | `test_id: string`、`expected_result_suggestion: string`、`confidence: number`、`explanation: string`、`needs_review: boolean` | 可用于批准测试用例 | 修改 TestCase 状态 |
| PromptEvidence | `evidence_id: string`、`prompt_name: string`、`target_id: string`、`input: object`、`output: object`、`source_context_ids: array<string>`、`output_summary: string` | 只读 | 无 |
| RevisionLog | `id: string`、`step: number`、`entity_type: string`、`entity_id: string`、`field: string`、`old_value: string`、`new_value: string`、`reason: string`、`timestamp: string` | 只读 | 前端本地生成 |
| AnalysisResult | `requirement_id: string`、`coverage_item_id: string`、`test_id: string`、`status: enum<covered, missing, improved, needs_review>`、`gap: string`、`improvement: string` | 只读 | 无 |
| OptimizeResult | `objective: enum<set_cover, risk_priority>`、`before_count: number`、`after_count: number`、`kept_test_ids: array<string>`、`removed_test_ids: array<string>`、`coverage_preservation: array<string>`、`warnings: array<string>` | 只读 | 无 |

## 5. 关键接口契约

### 5.1 输入与解析

文本输入：

```json
POST /ingest
{
  "content": "需求文本"
}
```

成功返回 `204 No Content`。

文件输入：

```text
POST /ingest/file
multipart/form-data: file
```

成功返回 `204 No Content`。

结构化解析：

```json
POST /parse
{
  "requirement_text": "需求文本",
  "rag_context": null
}
```

PDF/DOCX 文件上传后的结构化解析：

```json
POST /parse
{
  "requirement_text": "",
  "rag_context": null
}
```

此时后端应从最近一次 `/ingest/file` 写入的暂存内容中抽取需求文本。

前端读取：

```json
{
  "requirements": [],
  "analyzed_requirements": [],
  "prompts_used": []
}
```

### 5.2 风险评分

```json
POST /risk
{
  "analyzed_requirements": [],
  "rag_context": null
}
```

前端读取 `risk_analysis`，并映射为页面中的 `RiskEntry`。

### 5.3 覆盖项与策略

覆盖目标识别：

```json
POST /coverage
{
  "analyzed_requirements": [],
  "risk_analysis": []
}
```

前端读取 `coverage_goals`。

覆盖策略分配：

```json
POST /strategy
{
  "coverage_goals": [],
  "analyzed_requirements": [],
  "risk_analysis": []
}
```

前端读取 `coverage_items`，并在页面中展示覆盖内容、测试技术、策略理由和技术理由。

### 5.4 测试用例、FSM 与 Oracle

测试用例生成：

```json
POST /generate
{
  "coverage_items": [],
  "risk_analysis": [],
  "rag_context": null
}
```

前端读取 `test_cases`，并允许设计者修改标题、步骤、期望结果和状态。

FSM 生成：

```json
POST /fsm
{
  "session_id": "SESSION-CURRENT",
  "requirements": [],
  "parsed_requirements": [],
  "coverage_items": []
}
```

前端读取 `fsm.mermaid` 和 `fsm.coverage_paths`。

Oracle 复核：

```json
POST /oracle
{
  "session_id": "SESSION-CURRENT",
  "test_cases": [],
  "requirements": []
}
```

前端读取 `oracle_results`，低置信度或 `needs_review=true` 时提示设计者复核。

### 5.5 改进、分析、优化与导出

差量再生成：

```json
POST /regenerate
{
  "session_id": "SESSION-CURRENT",
  "revision_id": "REV-*"
}
```

结果分析：

```json
POST /analysis
{
  "session_id": "SESSION-CURRENT"
}
```

测试套件优化：

```json
POST /optimize
{
  "session_id": "SESSION-CURRENT",
  "test_cases": [],
  "coverage_items": [],
  "risk_results": [],
  "objective": "risk_priority",
  "preserve_high_risk_unique_coverage": true
}
```

导出：

```json
POST /export
{
  "session_id": "SESSION-CURRENT",
  "format": "json",
  "include_revisions": true,
  "include_prompt_evidence": true,
  "test_case_status": "all"
}
```

## 6. 交互式修改要求

前端必须支持设计者至少修改以下四类设计项：

1. 结构化需求：修订输入字段、条件、期望行为，并确认需求有效。
2. 风险评分：调整风险等级和测试优先级。
3. 覆盖项：新增、删除、修改描述、修改测试技术、标记有效或无效。
4. 测试用例：修改标题、步骤、期望结果、状态。

当前前端会在本地生成 `RevisionLog`，用于页面展示修订证据轨。若需要后端持久化修订记录，应将本地 `RevisionLog` 映射为 `POST /revisions` 的请求体：

```json
{
  "session_id": "SESSION-CURRENT",
  "target_type": "coverage_item | test_case | risk_result | requirement",
  "target_id": "COV-AUT-*",
  "before": {},
  "after": {},
  "reason": "设计者修改原因",
  "created_by": "designer"
}
```

## 7. 前端展示状态要求

| 状态 | 展示要求 |
|---|---|
| loading | 长任务接口必须有加载状态，尤其是 `/parse`、`/generate`、`/fsm`、`/regenerate` |
| error | 展示后端错误信息或通用失败提示 |
| empty | 没有输入或没有生成结果时展示空状态，不使用假数据伪装成功 |
| local fallback | 后端未返回结果时，页面展示空数据并标记服务待接入 |
| revision pending | 人工修改后展示本地 Revision 证据轨 |
| regenerated | 差量再生成后展示新增、更新、未变化、废弃对象数量 |

## 8. 前端不负责的内容

- 不负责 RAG、LLM、Prompt 的实现。
- 不负责 EP、BVA、DT、FSM 算法。
- 不负责后端数据持久化。
- 不负责 AUT pytest 执行。
- 不决定测试套件优化中最终删除或保留哪些用例。
