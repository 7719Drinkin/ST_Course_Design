# 算法模块对接文档

## 1. 文档目标

本文档面向 E 算法负责人，用于明确 EP、BVA、DT、FSM 应该如何实现、如何交给后端包装、如何使用 RAG/Prompt 提供的语义结果，以及如何保证输出可追踪。

算法层不直接处理前端请求，不直接管理数据库，也不直接设计 Prompt。算法层接收后端传入的结构化数据，并返回可保存、可展示、可导出的结构化结果。

## 2. 算法输入总约束

所有算法模块至少接收以下对象中的一部分：

| 输入对象 | 用途 |
|---|---|
| ParsedRequirement | 提供输入字段、数据范围、条件、期望行为 |
| CoverageItem | 指定需要覆盖的行为或风险点 |
| Strategy | 指定 EP、BVA、DT 或 FSM |
| RiskResult | 影响生成顺序、优先级和优化候选 |
| PromptEvidence | 提供 B 的语义解释和标准依据 |
| RevisionRecord | 支持差量再生成 |

算法输出的每条测试用例必须包含：

```json
{
  "test_id": "TC-AUT-*",
  "requirement_id": "REQ-AUT-*",
  "coverage_item_id": "COV-AUT-*",
  "technique": "EP | BVA | DT | FSM",
  "preconditions": [],
  "test_steps": [],
  "expected_result": "",
  "standard_ref": ""
}
```

## 3. 后端包装方式

算法层建议暴露为 Python service 函数，由后端 Service 层调用。

```python
generate_ep_cases(parsed_requirement, coverage_item, strategy, risk_result=None) -> list[TestCase]
generate_bva_cases(parsed_requirement, coverage_item, strategy, risk_result=None) -> list[TestCase]
generate_dt_cases(parsed_requirement, coverage_item, strategy, risk_result=None) -> list[TestCase]
generate_fsm_model(parsed_requirements, coverage_items, strategy=None) -> FsmResult
regenerate_cases(revision_record, current_design_state) -> RegenerationResult
optimize_suite(test_cases, coverage_items, risk_results, objective) -> OptimizationCandidate
```

后端负责把这些函数包装成 `/generate`、`/fsm`、`/regenerate`、`/optimize`。

## 4. EP 生成器

### 4.1 输入

| 字段 | 来源 |
|---|---|
| `input_fields` | `/parse` 输出 |
| `data_ranges` | `/parse` 输出 |
| `conditions` | `/parse` 输出 |
| `expected_action` | `/parse` 输出 |
| `coverage_item_id` | `/coverage` 输出 |
| `standard_ref` | B 的策略建议或 RAG 证据 |

### 4.2 生成逻辑

1. 识别输入域。
2. 根据条件划分 valid partitions 和 invalid partitions。
3. 每个分区选择代表值。
4. 为每个代表值生成测试用例。
5. 保证每条用例绑定 `requirement_id` 和 `coverage_item_id`。

### 4.3 输出

输出 EP 测试用例列表，并标记每条用例属于有效等价类或无效等价类。

## 5. BVA 生成器

### 5.1 输入

BVA 依赖 ParsedRequirement 中明确的数据范围，例如库存数量、会员 ID 范围、可借数量上限、日期范围等。

### 5.2 生成逻辑

对于数值边界，默认生成：

```text
min - 1
min
min + 1
max - 1
max
max + 1
```

对于非数值边界，例如字符串长度、日期、枚举数量，需要先转换为可比较边界，再生成边界附近值。

### 5.3 输出

每条 BVA 用例必须说明：

- 边界字段；
- 边界值；
- 测试值；
- 预期结果；
- 对应覆盖项。

## 6. DT 生成器

### 6.1 输入

DT 依赖条件组合，主要来自：

- ParsedRequirement 的 `conditions`；
- B 的 Prompt 对业务规则的解释；
- CoverageItem 中的条件组合覆盖项。

### 6.2 生成逻辑

1. 将条件转换为布尔或枚举条件。
2. 构造 condition matrix。
3. 根据业务规则推导 action。
4. 合并等价规则，减少重复测试。
5. 为每条规则生成测试用例。

### 6.3 输出

DT 输出应包含：

```json
{
  "decision_table_id": "DT-AUT-*",
  "conditions": [],
  "rules": [],
  "actions": [],
  "test_cases": []
}
```

## 7. FSM 建模器

### 7.1 输入

FSM 主要用于 AUT 借阅和归还流程，输入包括：

- 状态：如可借、已借、已还、不可借；
- 事件：借书、还书、查询、失败操作；
- 条件：库存是否大于 0、会员是否存在、图书是否存在；
- 动作：创建借阅记录、更新库存、更新借阅状态。

状态语义可以由 B 的 Prompt 辅助提取，最终结构由 E 规范化。

### 7.2 生成逻辑

1. 识别状态集合。
2. 识别事件和迁移条件。
3. 构造状态迁移表。
4. 计算 All States 和 All Transitions 覆盖路径。
5. 输出 Mermaid 图描述文本。
6. 为迁移路径生成测试用例。

### 7.3 输出

```json
{
  "states": [],
  "transitions": [],
  "coverage_paths": [],
  "mermaid": "stateDiagram-v2 ...",
  "test_cases": []
}
```

## 8. 与 RAG/Prompt 的连接方式

算法层不直接拼 Prompt，也不直接调用模型。推荐连接方式：

```text
后端
-> 调用 B 获取语义候选、策略建议、standard_ref
-> 调用 E 做确定性生成
-> 必要时再调用 B 补充 expected_result 或解释
-> 保存结果
```

| 算法步骤 | 需要 B 提供什么 | E 使用方式 |
|---|---|---|
| 覆盖项规范化 | 候选覆盖项、生成理由 | 去重、编号、补齐字段 |
| 策略参数化 | technique 建议、standard_ref | 转换为 EP/BVA/DT/FSM 参数 |
| EP 生成 | 输入域解释、标准依据 | 划分等价类并生成用例 |
| BVA 生成 | 边界字段解释、范围含义 | 生成边界附近值 |
| DT 生成 | 条件和动作语义 | 构造决策表 |
| FSM 建模 | 状态、事件、条件候选 | 生成状态图和覆盖路径 |
| Oracle | expected result 建议 | 填充或审查 expected_result |

## 9. 差量再生成

当设计者修改覆盖项、策略或测试用例后，E 不应全量重跑所有测试用例。

差量再生成流程：

1. 后端传入 RevisionRecord。
2. E 根据 `target_type` 判断影响范围。
3. 若修改覆盖项，只更新该覆盖项关联的策略和测试用例。
4. 若修改策略，只更新该策略下的测试用例。
5. 若修改测试用例，优先保留人工修改，只补充受影响的追踪关系。

输出必须区分：

- `created`：新增对象；
- `updated`：更新对象；
- `unchanged`：未变化对象；
- `deprecated`：建议废弃对象。

## 10. 测试套件优化

测试套件优化由 D 主责，E 负责提供算法候选。

E 可提供两种模式：

| 模式 | 目标 | 输出 |
|---|---|---|
| set cover | 用尽量少的测试用例覆盖所有覆盖项 | 保留候选、删除候选、覆盖保持说明 |
| risk-priority | 优先保留高风险测试用例 | 按风险排序后的保留建议 |

硬性约束：

- 高风险唯一覆盖项不得删除；
- 删除任何用例必须说明仍由哪些用例覆盖相同覆盖项；
- 输出必须保留 `test_id`、`coverage_item_id` 和风险等级。
