# 前端展示对接文档

## 1. 文档目标

本文档面向 C 前端负责人，用于明确 AutoTestDesign 的前端页面需要接收什么输入、展示什么内容、允许设计者修改什么内容，以及每个页面对应的后端接口。

前端的核心目标不是展示静态结果，而是让设计者完成以下交互式测试设计链路：

```text
需求输入
-> 结构化解析
-> 概念识别
-> 风险评分
-> 覆盖项识别
-> 覆盖策略选择
-> 测试用例生成
-> 人工审查与修订
-> 差量再生成
-> 结果分析
-> 导出
```

所有展示对象必须围绕 AUT `LibraryManagementSystem`，不能把 AutoTestDesign 本身作为测试对象。

## 2. 页面与接口总览

| 页面或模块 | 设计者输入 | 前端展示 | 后端接口 | 备注 |
|---|---|---|---|---|
| 需求输入页 | CSV、TXT、direct input、AUT SRS | 上传状态、输入预览、需求列表、错误信息 | `POST /ingest` | 生成或保留 `requirement_id` |
| 结构化解析页 | 选择需求、触发解析 | 输入字段、数据范围、条件、期望行为、置信度 | `POST /parse` | 支持人工修订 |
| 概念识别页 | 选择解析结果 | 业务对象、业务操作、状态、约束、证据 | `POST /concepts` | 概念必须来自 AUT |
| 风险分析页 | 选择需求或覆盖项 | Impact、Likelihood、Risk Score、Risk Level、Test Priority、风险热力图 | `POST /risk` | 支持人工调整并记录 Revision |
| 覆盖项页 | 选择需求、概念、风险结果 | `COV-AUT-*`、覆盖项描述、来源需求、状态 | `POST /coverage` | 支持新增、修改、删除、标记有效性 |
| 覆盖策略页 | 选择覆盖项 | EP、BVA、DT、FSM、选择理由、标准依据 | `POST /strategy` | 支持设计者修改策略 |
| 测试用例页 | 选择覆盖项和策略 | `TC-AUT-*`、前置条件、步骤、输入、期望结果、追踪关系 | `POST /generate` | 用例必须可追踪到需求和覆盖项 |
| FSM 页面 | 选择状态相关需求或覆盖项 | 状态、迁移、覆盖路径、Mermaid 图、FSM 测试用例 | `POST /fsm` | FSM 是可选加分项，但若实现必须可展示 |
| Prompt 证据页 | 选择生成步骤 | Prompt 模板、输入、RAG 上下文、模型输出摘要 | 由 `/parse`、`/coverage`、`/strategy`、`/generate`、`/analysis` 返回或查询 | 用于证明 LLM 参与过程透明 |
| Revision 面板 | 修改覆盖项、策略、用例、风险分数 | 修改前后内容、修改原因、影响范围 | `POST /revisions` | 所有人工修改都必须产生 `revision_id` |
| 差量再生成入口 | 选择一个 `revision_id` | 受影响项、新增或更新用例、变更说明 | `POST /regenerate` | 不应全量重跑所有内容 |
| 结果分析页 | 选择当前设计会话 | 需求、覆盖项、策略、用例之间的映射、遗漏项、改进项 | `POST /analysis` | 支持 D 做验收证据 |
| 测试套件优化页 | 选择测试用例集合和优化目标 | 保留用例、删除用例、覆盖保持说明、优化前后对比 | `POST /optimize` | D 主责优化取舍，E 协助算法 |
| 导出页 | 选择导出格式 | 导出预览、字段完整性、下载状态 | `GET /export` 或 `POST /export` | 至少支持 JSON、CSV、XLSX |

## 3. 前端必须支持的输入

| 输入类型 | 前端要求 | 校验要求 | 交给后端的字段 |
|---|---|---|---|
| CSV | 文件上传，显示文件名和行数 | 文件类型、空文件、编码错误 | `source_type: "csv"`、`content` 或 `file` |
| TXT | 文件上传，显示文本预览 | 文件类型、空文件、编码错误 | `source_type: "txt"`、`content` 或 `file` |
| direct input | 多行文本框 | 非空、长度提示 | `source_type: "direct"`、`content` |
| AUT SRS | 文件或文本输入 | 标记为 AUT 需求来源 | `source_type: "srs"`、`content` |

前端不负责解析文件语义，只负责把输入传给 `/ingest`，并把后端返回的错误显示给设计者。

## 4. 前端必须展示的数据对象

| 数据对象 | 必须展示字段 | 是否可编辑 | 编辑接口 |
|---|---|---|---|
| Requirement | `requirement_id`、`raw_requirement`、`source` | 原始内容原则上只读 | 如需修改，走 `POST /revisions` |
| ParsedRequirement | `input_fields`、`data_ranges`、`conditions`、`expected_action`、`confidence` | 可编辑 | `POST /revisions` |
| Concept | `concept_id`、`name`、`type`、`evidence` | 可标记有效性 | `POST /revisions` |
| RiskResult | `impact`、`likelihood`、`risk_score`、`risk_level`、`test_priority`、`reason` | 可调整 | `POST /revisions` |
| CoverageItem | `coverage_item_id`、`requirement_id`、`description`、`technique`、`status` | 可新增、修改、删除、标记有效 | `POST /revisions` |
| Strategy | `strategy_id`、`coverage_item_id`、`technique`、`standard_ref`、`reason` | 可编辑 | `POST /revisions` |
| TestCase | `test_id`、`requirement_id`、`coverage_item_id`、`test_steps`、`expected_result` | 可编辑 | `POST /revisions` |
| PromptEvidence | `prompt_template_id`、`prompt_inputs`、`source_context_ids`、`model_name`、`output_schema_version` | 只读 | 无 |
| RevisionRecord | `revision_id`、`target_type`、`target_id`、`before`、`after`、`reason` | 只读 | 无 |
| AnalysisResult | `requirement_id`、`coverage_item_id`、`test_id`、`status`、`gap`、`improvement` | 只读或备注 | 可通过 `POST /revisions` 新增改进项 |

## 5. 交互式修改要求

前端必须支持设计者至少修改以下三类设计项：

1. 覆盖项：新增、删除、修改描述、标记有效或无效。
2. 覆盖策略：把一个覆盖项从 EP 改为 BVA、DT 或 FSM，或修改策略理由。
3. 测试用例：修改步骤、输入数据、期望结果、风险等级或状态。

每次修改必须提交：

```json
{
  "session_id": "SESSION-*",
  "target_type": "coverage_item | strategy | test_case | risk_result",
  "target_id": "COV-AUT-*",
  "before": {},
  "after": {},
  "reason": "设计者修改原因",
  "created_by": "designer"
}
```

前端不得只在本地状态中修改数据而不调用 `POST /revisions`。没有 `revision_id` 的修改不能作为最终文档中的“基于证据的改进”。

## 6. 前端展示状态要求

| 状态 | 展示要求 |
|---|---|
| loading | 每个长任务接口必须有加载状态，尤其是 `/parse`、`/coverage`、`/generate`、`/fsm`、`/regenerate` |
| error | 展示后端错误信息、错误字段和建议操作 |
| empty | 没有输入或没有生成结果时展示空状态，不使用假数据伪装成功 |
| partial success | 有部分需求解析失败时展示成功项和失败项 |
| revision pending | 人工修改后展示是否已保存 Revision |
| regenerated | 差量再生成后展示新增、更新、未变化的对象 |

## 7. 前端不负责的内容

- 不负责 RAG、LLM、Prompt 的实现。
- 不负责 EP、BVA、DT、FSM 算法。
- 不负责后端数据持久化。
- 不负责 AUT pytest 执行。
- 不决定测试套件优化中最终删除或保留哪些用例。
