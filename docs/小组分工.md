# 小组分工（功能边界版）

## 0. 项目口径

本项目为 **AutoTestDesign（自动化测试设计工具）**，目标是实现一个面向软件测试设计的智能化工具。工具以 **AUT SRS**、需求样本和测试知识库为输入，结合 **RAG**、**LLM**、测试设计算法、交互式人工审查和前端可视化能力，帮助测试员完成测试设计、结果分析、证据改进和测试工件导出。

**AUT：** `LibraryManagementSystem`。三份主要交付文档 Risk Analysis Report（风险分析报告）、Test Plan（测试计划）、Detailed Test Design & Execution Document（详细测试设计与执行文档）的描述对象均为 AUT，而不是 AutoTestDesign（自动化测试设计工具）本身。

**设计者：** 指使用 AutoTestDesign（自动化测试设计工具）的测试员。老师要求中的“设计者参与”不是开发成员之间的沟通，而是测试员在工具中对 AUT 的测试设计结果进行审查、修订、验证和改进。

**核心边界原则：**

1. AutoTestDesign（自动化测试设计工具）是工具；`LibraryManagementSystem` 是 AUT。
2. 工具必须把交互式测试设计流程应用到 AUT 的测试中。
3. 工具必须支持设计者对覆盖项、覆盖策略和测试用例进行交互式修改。
4. API（应用程序接口）实现责任不等于算法责任。A 可以提供 `/fsm` 等 endpoint，但 FSM（有限状态机）核心建模算法由 E 负责。
5. 功能实现必须以统一 ID（标识符）贯通：`requirement_id`、`coverage_item_id`、`test_id`、`revision_id`、`prompt_template_id`、`source_context_ids`。

## 1. 交互式测试设计强制链路

老师要求的完整链路必须在工具功能中显式体现：

```text
概念
-> 覆盖项识别
-> 覆盖策略与方法
-> 测试用例及其设计的可追溯性
-> 提示设计
-> 结果分析
-> 基于证据的改进
```

该链路不是文档描述即可满足，而是必须在 AutoTestDesign（自动化测试设计工具）中形成可操作、可修改、可追踪、可导出的功能闭环。

| 链路步骤 | 工具必须体现的能力 | 主责 | 配合 | D 验收重点 |
|---|---|---|---|---|
| **概念** | 从 AUT SRS 和需求样本中识别业务概念，如图书、会员、借阅记录、借书、还书、可借、已借、已还 | B | A、C、E | 概念是否来自 AUT，是否可追踪到 `REQ-AUT-*` 或 `FR-AUT-*` |
| **覆盖项识别** | 让 LLM输出候选覆盖项，并由算法层规范化为 `COV-AUT-*` | B、E | A、C | 覆盖项是否覆盖 AUT 关键行为、边界、错误路径和状态迁移 |
| **覆盖策略与方法** | 为每个覆盖项选择 EP、BVA、DT、FSM（有限状态机）等测试方法，并说明依据 | B、E | C、D | 策略是否匹配需求类型，是否有 `standard_ref` |
| **测试用例及其设计的可追溯性** | 生成测试用例，并维护 `REQ-AUT-* -> COV-AUT-* -> TC-AUT-*` 追踪关系 | E | A、B、C | 每个测试用例是否能回溯到覆盖项和 AUT 需求 |
| **提示设计** | 设计 Prompt让 LLM输出黑盒测试相关的覆盖项、策略和测试用例草案，并保存 Prompt透明度证据 | B | A、C、D | 是否保留 `prompt_template_id`、输入、检索上下文、模型输出 |
| **结果分析** | 分析测试用例与覆盖项、覆盖策略、测试方法之间的映射关系 | D、E | B、C | 是否能说明哪些覆盖项已覆盖、哪些遗漏、哪些需要人工改进 |
| **基于证据的改进** | 设计者新增或修改有效覆盖项、策略、测试用例，工具记录 Revision（修订记录）并支持差量再生成 | C、A、E、B | D | 是否有 `REV-*` 记录，是否能证明新增项有效且来自证据 |

## 2. 术语说明

| 关键词 | 中文解释 | 在本项目中的含义 |
|---|---|---|
| AUT（被测应用） | Application Under Test，被测试的目标系统 | 本项目中指 `LibraryManagementSystem` |
| SRS（软件需求规格说明） | Software Requirements Specification，描述系统需求的文档 | 本项目中指 AUT（被测应用）的需求规格说明 |
| endpoint（接口入口） | 一个具体可调用的 API（应用程序接口）路径 | 如 `/fsm`、`/export` |
| EP （等价类划分）| Equivalence Partitioning，黑盒测试设计方法 | 将输入划分为有效等价类和无效等价类 |
| BVA （边界值分析）| Boundary Value Analysis，黑盒测试设计方法 | 针对边界值及其邻近值生成测试 |
| DT （决策表测试）| Decision Table Testing，黑盒测试设计方法 | 针对条件组合和业务规则生成测试 |
| FSM（有限状态机） | Finite State Machine，状态迁移建模方法 | 用于 AUT（被测应用）借阅/归还流程的状态建模和路径覆盖 |
| Oracle（预期结果判定） | 判断测试输入对应的期望输出是否合理 | 用于生成或审查测试用例的 `expected_result` |
| RAGAS（RAG 评价指标工具） | 用于评价 RAG输出质量的指标工具 | 用于评价 RAG是否提升 AUT（被测应用）需求理解和测试设计质量 |
| Revision（修订记录） | 设计者修改覆盖项、策略或测试用例时保存的记录 | 用于证明交互式改进真实发生 |
| Traceability（可追溯性） | 测试工件之间的追踪关系 | 例如 `REQ-AUT-* -> COV-AUT-* -> TC-AUT-*` |

## 3. 功能点总览

| 功能点 | 对应要求 | 功能目标 | 主责 | 配合 | 关键边界 |
|---|---|---|---|---|---|
| F1 多源需求输入与归一化 | FR 1.0 | 从 CSV、TXT、direct input（直接文本输入）和 AUT SRS 中导入需求，转换为统一需求结构 | A | C、D | A 负责输入接口和格式归一化；C 负责上传/粘贴界面；D 提供 AUT SRS 和 15 条需求样本 |
| F2 需求结构化解析 | FR 1.1 | 从 AUT 原始需求中抽取输入字段、数据范围、条件和期望行为 | B | A、C、D、E | B 负责 LLM解析；A 包装 `/parse` 接口；C 展示和允许修订；D 用 15 条样本验收；E 消费解析结果 |
| F3 AUT 概念识别 | 交互式链路 | 识别 AUT 中的业务对象、操作、状态和约束 | B | A、C、D、E | 概念必须来自 AUT，不是来自 AutoTestDesign（自动化测试设计工具）本身 |
| F4 风险评分与测试优先级 | FR 2.0 | 对 AUT requirement（需求）或 coverage item（覆盖项）进行 Impact（影响程度）× Likelihood（发生可能性）评分，输出 High / Medium / Low（高/中/低）和测试优先级 | B | A、C、D、E | 风险评分对象是 `REQ-AUT-*`、`FR-AUT-*` 或 `COV-AUT-*`，不是成员任务或工具模块 |
| F5 覆盖项识别 | 交互式链路 | 生成并规范化 `COV-AUT-*` 覆盖项 | B、E | A、C、D | B 让 LLM输出候选覆盖项；E 去重、编号和结构化；C 允许设计者修改；D 验证覆盖充分性 |
| F6 覆盖策略与方法选择 | 交互式链路 | 为覆盖项选择 EP、BVA、DT、FSM（有限状态机）等方法 | B、E | C、D | B 提供策略建议和标准依据；E 转换为算法参数；C 允许设计者修改策略；D 验证策略合理性 |
| F7 黑盒测试用例生成 | FR 3.0 | 根据 EP、BVA、DT生成可追踪测试用例 | E | A、B、C、D | E 负责最终结构化生成；B 可提供 LLM草案和标准依据 |
| F8 FSM（有限状态机）状态迁移测试设计 | FR 4.0 可选加分 | 建模 AUT 状态行为，生成状态迁移图和覆盖路径 | E | A、B、C、D | E 负责 FSM（有限状态机）核心算法；A 只包装 `/fsm` 接口；C 只展示；D 验证是否服务 AUT 测试 |
| F9 Oracle（预期结果判定） | FR 5.0 可选加分 | 帮助生成或审查测试用例 expected result（期望结果） | B | A、C、D | B 负责语义判断；D 验证是否可作为 AUT 测试依据 |
| F10 Prompt设计与透明化 | 交互式链路 | 记录 LLM如何参与概念、覆盖项、策略和测试用例草案生成 | B | A、C、D | 必须保存 `prompt_template_id`、输入、检索上下文和模型输出摘要 |
| F11 交互式审查与修订 | 交互式链路 | 允许设计者修改覆盖项、覆盖策略和测试用例 | C、A | B、D、E | C 负责交互；A 保存 Revision（修订记录）；B/E 响应修订；D 验证证据 |
| F12 差量再生成 | 交互式链路 | 根据设计者修改，只重新生成受影响的覆盖项或测试用例 | E、B | A、C、D | E 负责算法差量生成；B 负责修订 Prompt；A 负责接口；D 验证改进有效 |
| F13 结果分析与映射 | 交互式链路 | 分析测试用例与覆盖项、覆盖策略、测试方法之间的映射 | D、E | B、C | D 判断证据是否充分；E 提供结构化映射；C 展示映射关系 |
| F14 基于证据的改进 | 交互式链路 | 记录设计者新增的有效覆盖项和测试用例，形成改进前后对比 | D、C、A、E | B | 必须有 `REV-*`、修改原因、影响范围和前后对比 |
| F15 输出与导出 | FR 6.0 | 导出 test cases（测试用例）、test suites（测试套件）、risk scores（风险评分）和 revision history（修订历史） | A | B、C、D、E | A 负责 JSON（结构化数据格式）、CSV、XLSX（Excel 表格文件）导出；E 提供测试套件；B 提供风险和 Prompt证据；D 验证字段完整 |
| F16 测试套件优化 | FR 7.0 可选加分 | 按风险或覆盖效率优化测试套件 | D | A、C、E | D 负责优化目标、优化执行证据和最终取舍；E 协助提供 set cover（集合覆盖）和风险排序算法；C 展示优化前后对比；A 包装 `/optimize` 接口 |
| F17 AUT pytest 执行与评价 | 测试执行 | 对 `LibraryManagementSystem` 运行 API（应用程序接口）测试并汇总结果 | D | A、B、C、E | D 测 AUT，不把 AutoTestDesign（自动化测试设计工具）当 AUT |
| F18 NFR（非功能需求）保障 | NFR | 覆盖性能、可用性、安全性、可维护性和技术选型 | A、B、C、D、E | 全员 | 每个角色负责自己模块的非功能质量，D 负责最终检查 |

## 4. 接口边界总览

接口边界用于说明前端、后端、RAG、LLM、算法和测试验收之间如何对接。接口命名可以随实现调整，但字段语义必须保持一致。

| 接口 | 中文说明 | 主要输入 | 主要输出 | 接口负责人 | 逻辑负责人 | 前端对接 | 测试验收 |
|---|---|---|---|---|---|---|---|
| `/ingest` | 多源需求输入接口 | CSV、TXT、direct input（直接文本输入）、AUT SRS | requirements（需求列表）、errors（错误列表） | A | A | C | D |
| `/parse` | 需求结构化解析接口 | `requirement_id`、`raw_requirement` | 输入字段、数据范围、条件、期望行为、置信度 | A | B | C | D |
| `/concepts` | AUT 概念识别接口 | AUT 需求、解析结果、检索上下文 | 业务对象、操作、状态、约束 | A | B | C | D |
| `/risk` | 风险评分接口 | `REQ-AUT-*`、`FR-AUT-*` 或 `COV-AUT-*` | Impact（影响程度）、Likelihood（发生可能性）、风险分数、风险等级、测试优先级 | A | B | C | D |
| `/coverage` | 覆盖项识别接口 | 解析结果、概念、风险、检索上下文 | `COV-AUT-*` 覆盖项、说明、状态 | A | B、E | C | D |
| `/strategy` | 覆盖策略接口 | 覆盖项、风险、需求类型 | EP、BVA、DT、FSM（有限状态机）策略和依据 | A | B、E | C | D |
| `/generate` | 黑盒测试用例生成接口 | 覆盖项、覆盖策略、解析结果、风险等级 | `TC-AUT-*` 测试用例、前置条件、步骤、期望结果、标准依据 | A | E | C | D |
| `/fsm` | FSM（有限状态机）建模接口 | 状态相关需求、条件、事件、动作 | 状态、迁移、覆盖路径、Mermaid（图描述文本）、FSM 测试用例 | A | E | C | D |
| `/oracle` | Oracle（预期结果判定）接口 | 测试用例、输入数据、需求上下文 | 预期结果建议、置信度、解释 | A | B | C | D |
| `/revisions` | Revision（修订记录）接口 | 设计者修改前后内容、修改对象、修改原因 | `REV-*`、修改历史、影响范围 | A | A | C | D |
| `/regenerate` | 差量再生成接口 | `revision_id`、受影响覆盖项、受影响策略或用例 | 新增或更新后的覆盖项、测试用例、映射关系 | A | E、B | C | D |
| `/analysis` | 结果分析接口 | 需求、覆盖项、策略、测试用例、修订记录 | 覆盖映射、遗漏项、改进前后对比 | A | D、E | C | D |
| `/optimize` | 测试套件优化接口 | 测试用例集合、风险等级、覆盖关系 | 保留用例、删除用例、覆盖保持说明 | A | D（E 协助算法） | C | D |
| `/export` | 输出导出接口 | 需求、风险、覆盖项、策略、用例、修订历史、分析结果 | JSON（结构化数据格式）、CSV、XLSX（Excel 表格文件） | A | A 聚合，B/E/D 提供数据 | C | D |

## 5. A — 后端与接口负责人

### 负责功能

A 负责后端基础设施、接口封装和数据持久化边界：

- F1 多源需求输入与归一化的 API（应用程序接口）；
- `/ingest` 接口支持 CSV、TXT、direct input（直接文本输入）和 AUT SRS 内容；
- 所有前端可调用 endpoint 的路由、请求校验和响应包装；
- 对 B 的 RAG、LLM能力进行接口封装；
- 对 E 的 EP、BVA、DT、FSM（有限状态机）能力和 D 的测试套件优化流程进行接口封装，其中优化算法由 E 协助提供；
- 保存 DesignSession（设计会话）、CoverageItem（覆盖项）、Strategy（覆盖策略）、TestCase（测试用例）、RevisionRecord（修订记录）；
- 提供交互式审查所需的新增、修改、查询、历史记录接口；
- 聚合导出所需的需求、风险评分、覆盖项、覆盖策略、测试用例、测试套件、Prompt证据、Revision（修订记录）证据和结果分析数据；
- 负责后端侧 NFR 中的安全配置、接口稳定性、错误响应和基础性能记录。

### 对接边界

| 功能点 | A 的输入 | A 的输出 | 对接对象 | 边界说明 |
|---|---|---|---|---|
| FR 1.0（功能需求 1.0）多源输入 | C 提交的 CSV、TXT、direct input（直接文本输入）和 AUT SRS；D 提供的 15-sample requirement set（15 条需求样本集） | `/ingest` API（应用程序接口）、统一 Requirement（需求）结构、错误列表 | C、D、B、E | A 只负责输入入口、格式归一化、字段校验和错误响应，不负责判断需求语义是否正确 |
| FR 1.1（功能需求 1.1）结构化解析 | B 的 LLM（大语言模型）解析能力和 Prompt（提示词）输出 | `/parse` API（应用程序接口）、解析结果包装、mock data（模拟数据） | B、C、D、E | B 负责解析逻辑，A 负责接口封装、请求校验、响应格式和持久化 |
| FR 2.0（功能需求 2.0）风险评分 | B 的风险评分结果、D 的风险对象验收规则 | `/risk` API（应用程序接口）、RiskResult（风险结果）保存与查询 | B、C、D、E | B 负责评分逻辑，A 负责接口和数据保存，不替 B 决定分数 |
| F16 测试套件优化 | D 的优化目标、测试用例集合、覆盖关系、风险等级；E 的优化算法辅助 | `/optimize` API（应用程序接口）和优化结果包装 | D、E、C | D 是优化任务主责，A 只提供接口；E 提供算法辅助，A 不决定保留或删除哪些测试用例 |
| NFR（非功能需求） | 全组接口调用方式、环境变量、异常场景、性能目标 | 后端安全配置、错误响应、基础性能记录、接口稳定性证据 | 全员、D | A 负责后端侧 NFR（非功能需求），D 负责最终检查，C/B/E 分别负责各自模块质量 |

### 不负责功能

A 不负责：

- 设计 Prompt 或判断 LLM 输出质量；
- 实现 EP、BVA、DT、FSM、套件优化等算法；
- 实现前端编辑体验；
- 编写 AUT pytest 测试；
- 判断测试设计是否充分。

## 6. B — RAG、LLM与 Prompt负责人

### 负责功能

B 负责所有与 RAG、LLM、Prompt 有关的智能生成能力：

- F2 需求结构化解析：从 AUT requirement（需求）中抽取 `input_fields`、`data_ranges`、`conditions`、`expected_action`；

- F4 风险评分：对 `REQ-AUT-*`、`FR-AUT-*` 或 `COV-AUT-*` 进行 Impact（影响程度）和 Likelihood（发生可能性）评分，输出 Risk Score（风险分数）、Risk Level（风险等级）和 Test Priority（测试优先级）；
- F5 覆盖项识别 Prompt ：让 LLM输出黑盒测试相关覆盖项，例如有效借书、库存为 0、未知图书、未知会员、重复归还；

- F9 Oracle（预期结果判定）：帮助生成或审查测试用例 expected result（期望结果）；
- F10 Prompt透明化：保存 `prompt_template_id`、Prompt输入、检索上下文、模型名称、输出结构版本；
- F12 修订 Prompt：当设计者修改覆盖项或策略后，让 LLM基于 RevisionRecord（修订记录）重新分析受影响内容；
- 提供 RAGAS（RAG 评价指标工具）和 A/B 对比所需的 RAG输出样本。

| 测试套件优化 | `/optimize` | 可补充风险解释 | 展示优化前后对比 | 主责优化目标、取舍和证据 | 协助提供优化算法候选 |
| 导出 | `/export` | 提供风险和 Prompt证据 | 展示导出入口 | 验证导出可用 | 提供测试套件和优化候选结果 |
| NFR（非功能需求） | 安全、接口稳定、性能记录 | Prompt和 RAG可控 | 可用性 | 最终检查 | 算法效率和可维护性 |

## 12. 冲突处理规则

1. 如果某功能同时包含 API（应用程序接口）和算法，A 负责 API（应用程序接口），E 负责算法。
2. 如果某功能同时包含 LLM与确定性算法，B 负责 LLM/RAG/Prompt，E 负责确定性算法。
3. 如果某功能同时包含展示和生成，C 负责展示交互，B/E 负责生成逻辑。
4. 如果某功能进入最终测试证据，D 负责验证证据真实性、可追踪性和可复现性。
5. 任何覆盖项、策略、测试用例的人工修改都必须产生 `revision_id`，否则不能作为“基于证据的改进”写入最终文档。
