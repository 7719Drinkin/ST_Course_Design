# 后端接口对接文档

## 1. 文档目标

本文档面向 A 后端负责人，用于明确后端需要为前端提供哪些 endpoint、每个 endpoint 的输入字段、返回字段、字段类型、业务逻辑，以及如何对接 B 的 RAG/Prompt 能力和 E 的测试设计算法。

后端职责是接口封装、请求校验、响应包装、数据持久化和流程编排。后端不负责 Prompt 设计，也不负责 EP、BVA、DT、FSM 的核心算法。

## 2. 通用字段类型约定

| 类型写法 | 含义 |
|---|---|
| `string` | 字符串 |
| `number` | 数值，包含整数和小数 |
| `boolean` | 布尔值 |
| `object` | JSON 对象 |
| `array<T>` | T 类型数组 |
| `enum<...>` | 枚举值，只能从列出的值中选择 |
| `file` | multipart 文件 |
| `binary` | 二进制文件流 |

通用 ID 规则：

| ID | 示例 | 含义 |
|---|---|---|
| `session_id` | `SESSION-001` | 一次测试设计会话 |
| `requirement_id` | `REQ-AUT-001` | AUT 需求 |
| `coverage_goal_id` | `CG-AUT-001-001` | 覆盖目标 |
| `coverage_item_id` | `COV-AUT-001-BVA-001` | 已分配测试技术的覆盖项 |
| `strategy_id` | `STR-AUT-001` | 覆盖策略 |
| `spec_id` | `SPEC-AUT-001-BVA-001` | 测试设计规格 |
| `test_id` | `TC-AUT-001-001` | 测试用例 |
| `revision_id` | `REV-001` | 人工修订记录 |
| `prompt_template_id` | `PROMPT-PARSE-001` | Prompt 模板 |
| `prompt_name` | `requirement_parse` | 当前 agent 记录的 Prompt 名称 |

当前 agent 记录的 Prompt 证据字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | `string` | Prompt 名称，如 `requirement_parse`、`test_design_spec` |
| `prompt` | `string` | 实际发送给模型的 Prompt 文本 |
| `coverage_item_id` | `string` | 可选；当 Prompt 针对单个覆盖项时记录 |
| `spec_id` | `string` | 可选；当 Prompt 针对单个测试设计规格时记录 |

当前 `backend.agent.generate_blackbox_tests(...)` 门面成功返回：

| 字段 | 类型 | 说明 |
|---|---|---|
| `success` | `boolean` | 是否成功 |
| `data` | `object` | 包含 `requirements`、`analyzed_requirements`、`risk_analysis`、`coverage_goals`、`coverage_items`、`test_design_specs`、`test_cases` |
| `metadata` | `object` | 包含 `case_count`、`coverage_item_count`、`requirement_count`、`techniques`、`has_rag_context` |
| `prompts_used` | `array<PromptRecord>` | Prompt 调用记录 |

## 3. Endpoint 设计

### 3.1 `POST /ingest`

**业务目标：** 接收设计者粘贴的需求文本，将原始文本写入后端暂存区，供后续解析流程读取。当前代码不在该接口中拆分需求、不生成 `REQ-AUT-*`，也不返回需求列表。

**请求格式：** `application/json`

**请求字段：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `content` | `string` | 否 | 文本内容；后端 schema 默认值为空字符串。前端应在提交前校验非空。 |

**返回字段：**

| HTTP 状态码 | 返回体 | 说明 |
|---|---|---|
| `204 No Content` | 无 | 写入成功；当前接口不返回 JSON。 |

**业务逻辑：**

1. 读取 JSON 中的 `content` 字段。
2. 将 `content` 按 UTF-8 编码为 `bytes`。
3. 调用 `ingest_manager.ingest(...)` 写入后端暂存文件。
4. 返回 `204 No Content`。
5. 当前代码不做需求拆分、ID 生成、会话保存或错误项列表返回。

**文件上传补充入口：** 当前代码另有 `POST /ingest/file`，用于文件上传。它不属于 `POST /ingest` 的 JSON 请求体，但前端文件上传应调用该入口。

`POST /ingest/file` 请求格式：`multipart/form-data`

`POST /ingest/file` 请求字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `file` | `file` | 是 | multipart 文件字段；后端读取原始 `bytes`，并根据文件名后缀记录格式。 |

`POST /ingest/file` 返回字段：

| HTTP 状态码 | 返回体 | 说明 |
|---|---|---|
| `204 No Content` | 无 | 写入成功；当前接口不返回 JSON。 |

文件解析说明：

1. `.txt`、`.md` 按 UTF-8 文本解析。
2. `.pdf` 依赖 `pymupdf`。
3. `.docx` 依赖 `python-docx`。
4. `.doc` 当前解析器会抛出 `NotImplementedError`。
5. 未注册后缀会按 UTF-8 容错解码。

**B/E 对接：** 不调用 B 或 E。

### 3.2 `POST /parse`

**业务目标：** 执行当前 agent 工作流中的 `RequirementParseAgent` 和 `RequirementAnalysisAgent`，先拆分原子需求，再抽取黑盒测试设计需要的输入、范围、条件、业务规则和期望行为。

**请求字段：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `requirement_text` | `string` | 是 | AUT 需求文本；当前 agent 入口使用整段文本启动解析 |
| `rag_context` | `string` | 否 | 可选检索上下文；解析阶段当前不强依赖 |

**返回字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `requirements` | `array<ParsedRequirement>` | `RequirementParseAgent` 产物 |
| `analyzed_requirements` | `array<AnalyzedRequirement>` | `RequirementAnalysisAgent` 产物 |
| `prompts_used` | `array<PromptRecord>` | 当前 agent 实际记录的 Prompt 调用 |

**`ParsedRequirement` 字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `requirement_id` | `string` | `REQ-AUT-*` |
| `module` | `string` | 需求所属业务模块 |
| `raw_text` | `string` | 原始需求文本片段 |
| `description` | `string` | 原子需求描述 |

**`AnalyzedRequirement` 字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `requirement_id` | `string` | 对应 ParsedRequirement |
| `module` | `string` | 需求所属业务模块 |
| `description` | `string` | 需求描述 |
| `input_fields` | `array<string>` | 输入字段 |
| `data_ranges` | `array<string>` | 数据范围或边界 |
| `conditions` | `array<string>` | 条件和约束 |
| `business_rules` | `array<string>` | 业务规则 |
| `expected_action` | `string` | 期望行为 |

**业务逻辑：**

1. 读取 `requirement_text`。
2. 调用 `RequirementParseAgent` 生成 `requirements`。
3. 调用 `RequirementAnalysisAgent` 生成 `analyzed_requirements`。
4. 校验实际产物字段，不要求当前 role 没有产出的 `confidence`、`missing_fields`、`source_context_ids`。
5. 返回解析和分析结果。

**B/E 对接：** 调用 B 的 LLM/Prompt 能力；不调用 E。

### 3.3 `POST /risk`

**业务目标：** 执行 `RiskAnalysisAgent`，对 `analyzed_requirements` 中的每条 AUT 需求进行风险评分。

**请求字段：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `analyzed_requirements` | `array<AnalyzedRequirement>` | 是 | `RequirementAnalysisAgent` 产物 |
| `rag_context` | `string` | 否 | 可选检索上下文 |

**返回字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `risk_analysis` | `array<RiskAnalysisItem>` | `RiskAnalysisAgent` 产物 |
| `prompts_used` | `array<PromptRecord>` | 当前 agent 实际记录的 Prompt 调用 |

**`RiskAnalysisItem` 字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `requirement_id` | `string` | 被评分需求 ID |
| `impact` | `number` | 1 到 5 的整数 |
| `likelihood` | `number` | 1 到 5 的整数 |
| `risk_score` | `number` | `impact * likelihood` |
| `risk_level` | `enum<High, Medium, Low>` | 风险等级 |
| `test_priority` | `enum<P1, P2, P3>` | 测试优先级 |
| `risk_reason` | `string` | 评分理由 |

**业务逻辑：**

1. 输入 `analyzed_requirements`。
2. 调用 `RiskAnalysisAgent`。
3. 校验 `impact`、`likelihood`、`risk_score`、`risk_level` 和 `test_priority` 的一致性。
4. 返回 `risk_analysis`。

**B/E 对接：** 调用 B 的 LLM/Prompt 能力；不调用 E。E 只消费风险结果。

### 3.4 `POST /coverage`

**业务目标：** 执行 `CoverageIdentificationAgent`，从结构化需求和风险结果中识别业务覆盖目标。当前阶段该接口对应的是 `coverage_goals`，还不分配 EP/BVA/DT 技术。

**请求字段：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `analyzed_requirements` | `array<AnalyzedRequirement>` | 是 | `RequirementAnalysisAgent` 产物 |
| `risk_analysis` | `array<RiskAnalysisItem>` | 是 | `RiskAnalysisAgent` 产物 |

**返回字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `coverage_goals` | `array<CoverageGoal>` | `CoverageIdentificationAgent` 产物 |
| `prompts_used` | `array<PromptRecord>` | 当前 agent 实际记录的 Prompt 调用 |

**`CoverageGoal` 字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `coverage_goal_id` | `string` | `CG-AUT-*` |
| `requirement_id` | `string` | 来源需求 |
| `goal` | `string` | 覆盖目标描述 |
| `related_inputs` | `array<string>` | 相关输入字段 |
| `related_conditions` | `array<string>` | 相关条件 |
| `expected_action` | `string` | 期望行为 |

**业务逻辑：**

1. 将 `analyzed_requirements` 和 `risk_analysis` 传给 `CoverageIdentificationAgent`。
2. 只生成覆盖目标，不分配测试技术。
3. 校验 `coverage_goal_id`、`requirement_id`、`goal`、`related_inputs`、`related_conditions`、`expected_action`。
4. 返回 `coverage_goals`。

**B/E 对接：** 调用 B 的 LLM/Prompt 能力；当前不调用 E。

### 3.5 `POST /strategy`

**业务目标：** 执行 `TechniqueAssignmentAgent`，把 `coverage_goals` 转换成已分配单一黑盒测试技术的 `coverage_items`。当前 agent 没有独立 `Strategy` 产物，策略理由内嵌在 `coverage_items` 中。

**请求字段：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `coverage_goals` | `array<CoverageGoal>` | 是 | `CoverageIdentificationAgent` 产物 |
| `analyzed_requirements` | `array<AnalyzedRequirement>` | 是 | `RequirementAnalysisAgent` 产物 |
| `risk_analysis` | `array<RiskAnalysisItem>` | 是 | `RiskAnalysisAgent` 产物 |

**返回字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `coverage_items` | `array<CoverageItem>` | `TechniqueAssignmentAgent` 产物 |
| `prompts_used` | `array<PromptRecord>` | 当前 agent 实际记录的 Prompt 调用 |

**`CoverageItem` 字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `coverage_item_id` | `string` | `COV-AUT-*`，最终会被规范化为包含需求编号和技术的 ID |
| `coverage_goal_id` | `string` | 来源覆盖目标 |
| `requirement_id` | `string` | 来源需求 |
| `technique` | `enum<EP, BVA, DT>` | 当前 agent 只允许 EP、BVA、DT，不生成 FSM |
| `description` | `string` | 覆盖项描述 |
| `conditions` | `array<string>` | 相关条件 |
| `data_ranges` | `array<string>` | 数据范围或边界 |
| `input_fields` | `array<string>` | 相关输入字段 |
| `expected_action` | `string` | 期望行为 |
| `strategy_rationale` | `string` | 覆盖策略摘要 |
| `technique_reason` | `string` | 选择该技术的理由 |

**业务逻辑：**

1. 输入 `coverage_goals`、`analyzed_requirements` 和 `risk_analysis`。
2. 调用 `TechniqueAssignmentAgent`。
3. 为每个覆盖项分配且只分配一个 `EP/BVA/DT` 技术。
4. 校验 `coverage_goal_id`、`requirement_id`、`technique`、`strategy_rationale`、`technique_reason` 等实际产物字段。
5. 返回 `coverage_items`。

**B/E 对接：** 调用 B 的 LLM/Prompt 能力；当前不调用独立 E 参数化服务。

### 3.6 `POST /generate`

**业务目标：** 执行 `TestDesignSpecAgent` 和 `TestCaseDraftAgent`，先把 `coverage_items` 展开成测试设计规格，再生成可追踪测试用例。

**请求字段：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `coverage_items` | `array<CoverageItem>` | 是 | `TechniqueAssignmentAgent` 产物 |
| `risk_analysis` | `array<RiskAnalysisItem>` | 否 | 用于设置测试优先级 |
| `rag_context` | `string` | 否 | 可选标准上下文；缺省时 pipeline 会在设计规格阶段前检索 |

**返回字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `test_design_specs` | `array<TestDesignSpec>` | `TestDesignSpecAgent` 产物 |
| `test_cases` | `array<TestCaseDraft>` | `TestCaseDraftAgent` 产物 |
| `prompts_used` | `array<PromptRecord>` | 当前 agent 实际记录的 Prompt 调用 |

**`TestDesignSpec` 字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `spec_id` | `string` | `SPEC-AUT-*` |
| `coverage_item_id` | `string` | 来源覆盖项 |
| `requirement_id` | `string` | 来源需求 |
| `technique` | `enum<EP, BVA, DT>` | 与覆盖项技术一致 |
| `design_points` | `array<object>` | EP 分区、BVA 边界点或 DT 规则等设计点 |
| `standard_ref` | `string` | 标准依据 |

**`TestCaseDraft` 字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `test_id` | `string` | `TC-AUT-*` |
| `requirement_id` | `string` | 来源需求 |
| `coverage_item_id` | `string` | 来源覆盖项 |
| `spec_id` | `string` | 来源测试设计规格 |
| `technique` | `enum<EP, BVA, DT>` | 测试技术 |
| `title` | `string` | 用例标题 |
| `preconditions` | `array<string>` | 前置条件 |
| `input_data` | `object` | 测试输入 |
| `test_steps` | `array<string>` | 测试步骤 |
| `expected_result` | `string` | 期望结果 |
| `standard_ref` | `string` | 标准依据 |
| `priority` | `enum<P1, P2, P3>` | 来自风险结果的测试优先级 |
| `status` | `enum<Draft>` | 当前 agent 固定生成 Draft |

**业务逻辑：**

1. 读取 `coverage_items` 和 `risk_analysis`。
2. 若没有 `rag_context`，pipeline 在 `TestDesignSpecAgent` 前检索标准上下文。
3. 对每个覆盖项调用 `TestDesignSpecAgent` 生成 `test_design_specs`。
4. 对每个测试设计规格调用 `TestCaseDraftAgent` 生成 `test_cases`。
5. 单独的生成阶段只返回 `GenerateResult`；若通过完整 `generate_blackbox_tests(...)` 门面执行，则由 finalizer 统一执行 ID 规范化、追溯检查和最终质量门禁。

**B/E 对接：** 当前代码调用 B 的 LLM/Prompt 能力生成设计规格和用例草案；不调用独立 E EP/BVA/DT/FSM 生成器。

### 3.7 `POST /fsm`

**业务目标：** 生成 FSM 状态迁移模型和状态迁移测试用例。

**请求字段：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `session_id` | `string` | 是 | 设计会话 ID |
| `requirements` | `array<Requirement>` | 否 | 状态相关需求 |
| `parsed_requirements` | `array<ParsedRequirement>` | 否 | 状态相关解析结果 |
| `coverage_items` | `array<CoverageItem>` | 否 | 状态相关覆盖项 |
| `state_candidates` | `array<string>` | 否 | 前端或 B 提供的候选状态 |

**返回字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `session_id` | `string` | 设计会话 ID |
| `fsm` | `FsmResult` | FSM 模型 |
| `test_cases` | `array<TestCase>` | FSM 测试用例 |
| `prompt_evidence` | `array<PromptEvidence>` | 可选，状态语义提取证据 |

**`FsmResult` 字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `states` | `array<string>` | 状态集合 |
| `transitions` | `array<FsmTransition>` | 迁移集合 |
| `coverage_paths` | `array<string>` | 覆盖路径 |
| `mermaid` | `string` | Mermaid 图描述文本 |

**`FsmTransition` 字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `from` | `string` | 起始状态 |
| `to` | `string` | 目标状态 |
| `event` | `string` | 触发事件 |
| `condition` | `string` | 迁移条件 |
| `action` | `string` | 迁移动作 |

**业务逻辑：**

1. 输入状态相关需求、条件、事件和动作。
2. 调用 B 提取候选状态语义，或直接使用前端传入的状态候选。
3. 调用 E 的 FSM 建模器生成 states、transitions、coverage_paths。
4. 生成 Mermaid 图描述文本。
5. 返回 FSM 测试用例。

**B/E 对接：** 可调用 B；主调用 E。

**`OracleResult` 字段：**

| 字段 | 类型 | 说明 |

**返回字段：**

| `affected_ids` | `array<string>` | 受影响对象 ID |

**`RevisionRecord` 字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `revision_id` | `string` | `REV-*` |
| `session_id` | `string` | 设计会话 ID |

| `target_id` | `string` | 修改对象 ID |

| `created_by` | `string` | 修改者 |
| `created_at` | `string` | ISO 时间 |

**业务逻辑：**

1. 接收 target type、target id、before、after、reason。
2. 生成 `revision_id`。
3. 保存 RevisionRecord。
4. 更新目标对象状态为 `human_revised` 或 `human_added`。
5. 返回受影响对象列表。

**B/E 对接：** 不直接调用 B/E；`/regenerate` 消费 RevisionRecord。

### 3.10 `POST /regenerate`

**业务目标：** 根据 Revision 做差量再生成。

**请求字段：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `session_id` | `string` | 是 | 设计会话 ID |
| `revision_id` | `string` | 是 | 触发差量再生成的修订记录 |
| `current_state` | `object` | 否 | 当前设计状态快照 |

**返回字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `session_id` | `string` | 设计会话 ID |
| `created` | `object` | 新增对象，按类型分组 |
| `updated` | `object` | 更新对象，按类型分组 |
| `unchanged` | `object` | 未变化对象，按类型分组 |
| `deprecated` | `object` | 建议废弃对象，按类型分组 |
| `prompt_evidence` | `array<PromptEvidence>` | revision Prompt 证据 |

**业务逻辑：**

1. 读取 `revision_id`。
2. 分析受影响的需求、覆盖项、策略和测试用例。
3. 调用 B 重新解释修改影响。
4. 调用 E 只生成受影响用例。
5. 返回新增、更新、未变化和建议废弃对象。

**B/E 对接：** 先调用 B，再调用 E。

| `analysis_results` | `array<AnalysisResult>` | 映射和缺口分析 |

**`AnalysisResult` 字段：**

|---|---|---|

| `coverage_item_id` | `string` | 覆盖项 ID |

### 3.12 `POST /optimize`

**业务目标：** 进行测试套件优化。

**请求字段：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `session_id` | `string` | 是 | 设计会话 ID |
| `test_cases` | `array<TestCase>` | 是 | 待优化测试用例 |
| `coverage_items` | `array<CoverageItem>` | 是 | 覆盖项 |
| `risk_results` | `array<RiskResult>` | 是 | 风险结果 |
| `objective` | `enum<set_cover, risk_priority>` | 是 | 优化目标 |
| `preserve_high_risk_unique_coverage` | `boolean` | 否 | 是否强制保留高风险唯一覆盖，默认 `true` |

**返回字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `session_id` | `string` | 设计会话 ID |
| `optimization_result` | `OptimizationResult` | 优化结果 |

**`OptimizationResult` 字段：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `objective` | `enum<set_cover, risk_priority>` | 优化目标 |
| `before_count` | `number` | 优化前用例数 |

## 5. 后端错误响应要求

错误响应必须包含：

| 字段 | 类型 | 说明 |
|---|---|---|
| `error_code` | `string` | 错误码，如 `VALIDATION_ERROR` |
| `message` | `string` | 错误说明 |
| `field` | `string` | 可选，出错字段 |
| `details` | `object` | 可选，错误上下文 |

`ApiError` 与错误响应使用同一字段结构；endpoint 内的 `errors: array<ApiError>` 表示局部失败项，不代表整个请求失败。

不得只返回空字符串或未处理异常栈。
