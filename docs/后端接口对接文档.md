# 后端接口对接文档

## 1. 文档目标

本文档面向 A 后端负责人，用于明确后端需要为前端提供哪些接口、每个接口的业务逻辑是什么，以及接口如何连接 B 的 RAG/Prompt 能力和 E 的测试设计算法。

后端的职责是接口封装、请求校验、响应包装、数据持久化和流程编排。后端不负责 Prompt 设计，也不负责 EP、BVA、DT、FSM 的核心算法。

## 2. 总体服务分层

建议后端按以下层次组织：

```text
Router 层
-> Service 编排层
-> Domain 数据模型层
-> RAG/Prompt Adapter
-> Algorithm Adapter
-> Repository 持久化层
```

| 层次 | 主要职责 |
|---|---|
| Router | 暴露 endpoint，处理请求参数、状态码和错误响应 |
| Service | 编排 RAG、Prompt、算法、Revision、导出等业务流程 |
| Domain | 定义 Requirement、CoverageItem、TestCase 等统一结构 |
| RAG/Prompt Adapter | 调用 B 提供的解析、风险评分、覆盖项候选、策略建议和 Oracle |
| Algorithm Adapter | 调用 E 提供的 EP、BVA、DT、FSM、差量生成、优化候选 |
| Repository | 保存设计会话、需求、风险、覆盖项、用例、修订记录和导出结果 |

## 3. 核心数据对象

| 数据对象 | 必须字段 |
|---|---|
| Requirement | `requirement_id`、`raw_requirement`、`source` |
| ParsedRequirement | `requirement_id`、`input_fields`、`data_ranges`、`conditions`、`expected_action`、`confidence` |
| Concept | `concept_id`、`requirement_id`、`name`、`type`、`evidence` |
| RiskResult | `requirement_id` 或 `coverage_item_id`、`impact`、`likelihood`、`risk_score`、`risk_level`、`test_priority`、`reason` |
| CoverageItem | `coverage_item_id`、`requirement_id`、`description`、`technique`、`strategy`、`status` |
| Strategy | `strategy_id`、`coverage_item_id`、`technique`、`standard_ref`、`reason` |
| TestCase | `test_id`、`requirement_id`、`coverage_item_id`、`technique`、`preconditions`、`test_steps`、`expected_result`、`standard_ref` |
| PromptEvidence | `prompt_template_id`、`requirement_id`、`prompt_inputs`、`source_context_ids`、`model_name`、`output_schema_version` |
| RevisionRecord | `revision_id`、`target_type`、`target_id`、`before`、`after`、`reason`、`created_by` |
| AnalysisResult | `requirement_id`、`coverage_item_id`、`test_id`、`strategy_id`、`status`、`gap`、`improvement` |

## 4. Endpoint 设计

### 4.1 `POST /ingest`

**业务目标：** 接收前端输入的 CSV、TXT、direct input 或 AUT SRS，归一化为需求列表。

**请求核心字段：**

```json
{
  "session_id": "SESSION-*",
  "source_type": "csv | txt | direct | srs",
  "content": "原始文本",
  "filename": "optional"
}
```

**业务逻辑：**

1. 校验输入类型和内容是否为空。
2. 将不同来源统一拆分为 Requirement。
3. 为没有 ID 的需求生成 `REQ-AUT-*`。
4. 保存到 DesignSession。
5. 返回成功项和错误项。

**不做的事：** 不调用 LLM，不判断需求语义，不生成测试用例。

### 4.2 `POST /parse`

**业务目标：** 对需求进行结构化解析。

**连接对象：** B 的 requirement parse Prompt。

**业务逻辑：**

1. 读取 Requirement。
2. 调用 B 的 `parse_requirements` 能力。
3. 校验返回字段是否包含 `input_fields`、`data_ranges`、`conditions`、`expected_action`。
4. 保存 ParsedRequirement 和 PromptEvidence。
5. 返回解析结果和置信度。

### 4.3 `POST /concepts`

**业务目标：** 从 AUT 需求中识别业务概念。

**连接对象：** B 的 concept extraction Prompt。

**业务逻辑：**

1. 输入 Requirement 和 ParsedRequirement。
2. 调用 B 的概念识别能力。
3. 保存 Concept。
4. 返回业务对象、操作、状态、约束和证据。

### 4.4 `POST /risk`

**业务目标：** 对 AUT 需求或覆盖项进行风险评分。

**连接对象：** B 的 risk scoring Prompt 和风险矩阵。

**业务逻辑：**

1. 校验评分对象只能是 `REQ-AUT-*`、`FR-AUT-*` 或 `COV-AUT-*`。
2. 调用 B 的风险评分服务。
3. 保存 RiskResult。
4. 返回 Impact、Likelihood、Risk Score、Risk Level、Test Priority 和理由。

**关键约束：** 不允许对成员任务或工具模块评分。

### 4.5 `POST /coverage`

**业务目标：** 生成并规范化覆盖项。

**连接对象：** B 生成候选覆盖项，E 负责去重、编号和结构化。

**业务逻辑：**

1. 将解析结果、概念、风险结果传给 B。
2. B 返回候选覆盖项和理由。
3. 调用 E 的 coverage normalization。
4. 保存 CoverageItem。
5. 返回 `COV-AUT-*` 覆盖项列表。

### 4.6 `POST /strategy`

**业务目标：** 为覆盖项分配测试策略。

**连接对象：** B 提供策略建议和标准依据，E 转换为算法参数。

**业务逻辑：**

1. 输入 CoverageItem、RiskResult、ParsedRequirement。
2. 调用 B 生成策略建议。
3. 调用 E 生成算法可执行参数。
4. 保存 Strategy。
5. 返回 technique、standard_ref 和 reason。

### 4.7 `POST /generate`

**业务目标：** 生成可追踪测试用例。

**连接对象：** E 的 EP、BVA、DT 生成器；必要时接收 B 的 LLM 草案和标准依据。

**业务逻辑：**

1. 读取 CoverageItem、Strategy、ParsedRequirement、RiskResult。
2. 按 technique 调用 E 的对应生成器。
3. 若需要 expected result 或标准依据补充，调用 B 的 Prompt 或 Oracle。
4. 为每条测试用例生成 `TC-AUT-*`。
5. 校验每条用例必须包含 `requirement_id` 和 `coverage_item_id`。
6. 保存 TestCase。

### 4.8 `POST /fsm`

**业务目标：** 生成 FSM 状态迁移模型和状态迁移测试用例。

**连接对象：** E 的 FSM 建模器；B 可提供状态语义辅助。

**业务逻辑：**

1. 输入状态相关需求、条件、事件和动作。
2. 调用 B 提取候选状态语义，或直接使用前端传入的状态候选。
3. 调用 E 的 FSM 建模器生成 states、transitions、coverage paths。
4. 生成 Mermaid 图描述文本。
5. 返回 FSM 测试用例。

### 4.9 `POST /oracle`

**业务目标：** 生成或审查测试用例 expected result。

**连接对象：** B 的 Oracle Prompt。

**业务逻辑：**

1. 输入 TestCase、Requirement、RAG 上下文。
2. 调用 B 的 Oracle。
3. 返回 expected result 建议、置信度和解释。
4. 低置信度时标记人工复核。

### 4.10 `POST /revisions`

**业务目标：** 保存设计者人工修改。

**业务逻辑：**

1. 接收 target type、target id、before、after、reason。
2. 生成 `revision_id`。
3. 保存 RevisionRecord。
4. 更新目标对象状态为 `human_revised` 或 `human_added`。
5. 返回受影响对象列表。

**关键约束：** 所有覆盖项、策略和测试用例的人工修改都必须经过该接口。

### 4.11 `POST /regenerate`

**业务目标：** 根据 Revision 做差量再生成。

**连接对象：** B 的 revision Prompt，E 的差量生成器。

**业务逻辑：**

1. 读取 `revision_id`。
2. 分析受影响的需求、覆盖项、策略和测试用例。
3. 调用 B 重新解释修改影响。
4. 调用 E 只生成受影响用例。
5. 返回新增、更新和未变化的对象。

### 4.12 `POST /analysis`

**业务目标：** 生成结果分析和映射关系。

**业务逻辑：**

1. 汇总 Requirement、CoverageItem、Strategy、TestCase、RevisionRecord。
2. 生成 `REQ-AUT-* -> COV-AUT-* -> TC-AUT-*` 映射。
3. 标记已覆盖、未覆盖、需改进项。
4. 返回 AnalysisResult。

### 4.13 `POST /optimize`

**业务目标：** 进行测试套件优化。

**连接对象：** D 提供优化目标，E 提供算法候选。

**业务逻辑：**

1. 接收测试用例集合、风险等级、覆盖关系和优化目标。
2. 调用 E 的 set cover 或风险排序算法。
3. 返回保留用例、删除候选、覆盖保持说明。
4. 保存 D 最终接受或拒绝的优化结果。

**关键约束：** 高风险唯一覆盖项不得被删除。

### 4.14 `GET /export` 或 `POST /export`

**业务目标：** 导出测试设计工件。

**业务逻辑：**

1. 聚合需求、风险、覆盖项、策略、测试用例、测试套件、修订记录、Prompt 证据和分析结果。
2. 校验字段完整性。
3. 输出 JSON、CSV 或 XLSX。

## 5. 后端与 B/E 的调用关系

| 后端接口 | 调用 B | 调用 E |
|---|---|---|
| `/parse` | 结构化解析 Prompt | 不调用 |
| `/concepts` | 概念识别 Prompt | 不调用 |
| `/risk` | 风险评分 Prompt | 不调用 |
| `/coverage` | 覆盖项候选 Prompt | 覆盖项规范化 |
| `/strategy` | 策略建议 Prompt | 策略参数化 |
| `/generate` | 可选测试用例草案、Oracle、标准依据 | EP、BVA、DT 生成器 |
| `/fsm` | 可选状态语义辅助 | FSM 建模器 |
| `/oracle` | Oracle Prompt | 不调用 |
| `/regenerate` | revision Prompt | 差量生成 |
| `/optimize` | 可选风险解释 | 优化候选算法 |

## 6. 后端错误响应要求

错误响应必须包含：

```json
{
  "error_code": "VALIDATION_ERROR",
  "message": "错误说明",
  "field": "optional field name",
  "details": {}
}
```

不得只返回空字符串或未处理异常栈。
